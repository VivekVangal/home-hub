## Recently resolved

- [x] **Mobile nav redesigned as a hamburger + left slide-in drawer.** Below the existing 720px breakpoint, the squeezed horizontal link row and inline user info/sign-out hide in favor of a ☰ button that opens a full-height left drawer: icon + label for every page link, the signed-in user's name and email, and a sign-out button, all with room to breathe. Desktop is unchanged (same horizontal row it always had). Closes on link click, clicking outside the panel, or Escape. Tests in `NavBar.test.jsx` cover the hamburger opening the drawer, every link's accessible name (icon is `aria-hidden`, so it doesn't leak into the label), closing via link click / outside click / Escape, and sign-out.
- [x] **Training-plan feature confirmed working live on the dev site** — form-driven generator, private per-person, all confirmed by actually using it.
- [x] **Mini calendar added directly to the Training page.** A compact week-view calendar (reusing `WeekCalendar.jsx`, the same component `/calendar` uses, with a new `hideAddButton` prop) shows just the signed-in user's own training sessions with prev/next/today navigation, so training doesn't feel disconnected from the rest of the calendar system — because it isn't: training sessions are regular `events` docs, already visible on the real `/calendar` page too (just hidden from other family members there, per the existing privacy design). Clicking a session in the mini calendar marks it done. Tests in `WeekCalendar.test.jsx` (`hideAddButton` suppresses the add button) and `TrainingPage.test.jsx` (calendar renders, week navigation changes the displayed range, "Today" resets it).
- [x] **Strength/stretch sessions now name specific exercises with reference links.** Replaced the generic "Lower body + core, 30-40 min" text with a curated library (`frontend/src/lib/exercises.js`: 12 bodyweight strength moves + 6 stretches, runner-focused) that rotates through by week for variety. Each exercise links out to a YouTube search (not a hotlinked/embedded gif — avoids copyright risk and stale links) for anyone who wants to see the movement. Session events now carry `strengthExerciseIds`/`stretchExerciseIds` arrays (not just baked-into-text), which the Training page renders as clickable chips. Tests in `exercises.test.js` (rotation determinism/variety/no-duplicates, lookup) and `trainingPlan.test.js` (integration); ran the modules directly in plain `node` to confirm real output, same as VDOT below.
- [x] **VDOT training paces added alongside Riegel.** Riegel (in `analyzeGoal`) still predicts race-day finish time — a different question VDOT isn't meant to answer better. VDOT now derives a single fitness score from the same recent-race input and produces five distinct training paces (easy/marathon/threshold/interval/repetition) using Daniels & Gilbert's actual published regression equations (not an interpolated table), verified against the well-known VDOT-50-is-about-a-20:00-5k reference point. Quality-session notes now cite threshold/interval pace instead of one blended "stretch pace," and easy/long-run notes cite the VDOT easy pace — falling back to the old wording exactly when there's no recent race result to derive VDOT from. `computeVdot`/`vdotZonePace`/`vdotTrainingPaces` in `lib/trainingPlan.js`, tests in `trainingPlan.test.js` (including running the actual module in plain `node` to double check numbers, since vitest couldn't execute in this sandbox — see below).
- [x] **Training plan is now dynamic.** `computeTrainingAdjustment()` in `lib/trainingPlan.js` takes the last 3 weeks of already-logged sessions and adjusts upcoming weeks on regeneration: skipping more than a third of recent sessions slows the mileage ramp (never speeds it up — consistency is what should be rewarded), and consistently running logged sessions at or faster/slower than the stretch-goal pace nudges that goal by up to 3%. "Regenerate remaining plan" on the Training page now shows a note explaining what changed and why, when something did. Unit tests in `trainingPlan.test.js` (the adjustment function + `buildTrainingPlan` integration) and `TrainingPage.test.jsx` (`describeAdjustment`'s message text).
- [x] `scripts/setup.sh` step 3 idempotency bug — `ensure_firebase_project` now treats "already exists" as a successful no-op (instead of a hard `exit 1`) whether it's detected via `projects:list` or only surfaces when `projects:create` itself fails with that message. Covered by `scripts/setup.test.sh` (a plain-bash test with a stubbed `firebase` command — no test framework existed for shell scripts before this, only vitest for JS).
